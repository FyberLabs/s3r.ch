# Direct Kubo block transport (#570)

`createKuboBlockClient` is an unmounted browser adapter for a user-selected HTTPS Kubo RPC origin. It calls the documented [block put/get API](https://docs.ipfs.tech/reference/kubo/rpc/#api-v0-block-put) directly. There is no s3r.ch API proxy, default provider, gateway fallback, pinning or provisioning. No reader case is registered.

The caller must supply an explicitly approved endpoint, an authenticated current private grant, ciphertext from `sealMedia`, expected block CID/length from the authenticated manifest, and current consent. `current()` is checked before dispatch, while reading, and before returning. Abort the supplied signal immediately on revocation/account change; changing a callback alone cannot cancel an outstanding network read. The adapter does not authenticate grants, prove endpoint ownership, distinguish company aliases, or prove that input bytes are encrypted. Do not install it server-side or expose arbitrary endpoint input through a server route.

Endpoint configuration accepts only HTTPS origins without userinfo, paths, queries or fragments. Cookies, browser credentials and referrers are omitted; redirects are errors. This version does not accept provider tokens. The user's endpoint must permit the application origin through CORS and enforce its own access controls. **Do not expose the unrestricted Kubo administrative RPC publicly to make this adapter work.** A provider must expose only the required operations through its independently secured access boundary. That deployment is not created here.

Uploads explicitly select raw SHA-256 and `pin=false`; a matching receipt proves only acknowledged storage, not durability. The provider may garbage-collect unpinned bytes. Downloads must match both expected size and raw CID. `assembleMediaBlocks` and `openMedia` still must verify the complete ciphertext and authenticated encryption before display.

Each instance has two pending slots, 128 lifetime attempts, a caller-selected lifetime payload budget capped at 64 MiB, 1 MiB blocks, 1 KiB upload receipts and a ten-second operation deadline. Reservations include failed attempts. These are payload/admission limits, not wire bandwidth accounting; multipart/TLS overhead and browser buffering are outside the bound. The combined upload/download rolling-minute payload budget defaults to 1 MiB and can be explicitly set with `maxBytesPerMinute` from 1 byte to 8 MiB. An entire block must fit before admission; exhausted requests fail immediately without queueing or network traffic. Failed attempts retain their reservation until its minute expires. Monotonic time prevents wall-clock changes replenishing the budget. This caps admission bursts per rolling minute, not instantaneous socket throughput. The adapter makes one fetch call per admitted operation and performs no retry or fallback. Browsers may internally retransmit a disconnected request; those wire attempts are outside this payload admission counter. Use one instance per approved transfer session; constructing more instances does not enforce a cross-tab or account quota. An abort-ignoring injected transport retains its slot until settled.

Unit tests cover protocol, integrity, endpoint validation, lifetime/rolling budget consumption, exact expiry boundaries, invalid clocks, consent/cancellation, deadlines and occupied slots. PR CI runs real Chromium against a separate HTTPS loopback origin with actual multipart/CORS requests and real encrypted media. Fault cases reject tampered/truncated blocks and provider 503/disconnected uploads, with exactly one application fetch and no fallback. Chromium may internally retry a disconnected upload before reporting failure; the CI fixture records and bounds the observed provider attempts separately. Exhausted rate allowance sends no request. Cancellation and actual browser closure terminate a withheld upload acknowledgement; this does not prove deletion of already received bytes or interruption at a particular upload byte offset. Its provider is an explicit Kubo protocol substitute, not live Kubo or provider acceptance. TLS trust is relaxed only inside that isolated fixture.

Remaining #570 work includes native consent/grant mounting, provider access configuration and live evidence, shared transfer policy, multi-client provider/cache behavior and scheduled acceptance. Login and group sharing remain with their owners.


## Canonical block admission

Direct reads, cached reads and local cache read/write/eviction entry points share the manifest parser's strict raw CIDv1/SHA-256 validator. Wrong headers, nonzero base32 padding, uppercase forms and unsupported CID families fail before provider dispatch, shared transfer-slot/budget reservation, or IndexedDB access. Local writes also refuse malformed references before hashing their bytes. Invalid references do not consume a client's payload allowance; an explicit valid request can follow. Valid references still require returned-byte digest verification and the existing grant and whole-media authentication checks. Shape validation does not establish authority or availability.

Unit regressions verify zero provider/cache traffic and zero budget reservations for malformed references, valid-request recovery, and valid targeted eviction after close. Reader registration and native activation remain unchanged.
