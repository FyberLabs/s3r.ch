# Encrypted IPFS media transfer composition (#570)

`createIpfsMediaTransfer({blocks, current, signal})` connects `sealMedia`, raw block manifests, the existing Kubo client, complete-block verification and `openMedia`. This is an unmounted browser API. The caller must obtain provider selection, explicit consent, and authenticated current private grants from their existing owners. It does not create or distribute grants, authenticate users, register reader cases, pin data or provide a cloud fallback.

`upload(plaintext, binding)` encrypts locally with a fresh key, uploads ordered ciphertext blocks, verifies each returned CID and returns `{manifest, key}` only after every acknowledgement and a current-consent check. Put the key and authenticated manifest in the existing private grant channel; never public metadata. The manifest contains no key. A receipt is not durable availability. If a later block fails or consent is revoked, no grant is returned and the local key is overwritten. Earlier ciphertext blocks may remain at the provider. This does not erase peers' copies, roll back uploads, or retry/resume them.

`download(manifest, key, binding)` requires a bounded manifest, key and binding obtained from a current authenticated private grant. It retrieves blocks directly, checks expected sizes, all CIDs and complete digest, and verifies AES-GCM/binding before returning any plaintext. Provider faults, wrong key/binding, tampering and revocation fail closed. Private working key copies and retained ciphertext buffers are overwritten on completion; browser/crypto internals are outside this cleanup guarantee. The caller owns the successfully returned upload key and download plaintext and must manage their lifetime.

Use the same current callback and abort signal for composition and Kubo client. Abort immediately on revocation/account change. Callback checks alone cannot interrupt an outstanding fetch or Web Crypto operation. Each composition allows only one whole-media operation at a time and uses sequential block requests. It inherits the 64 MiB stored-media bound and retains whole-file copies; it is not a streaming codec or a claim of 64 MiB total heap usage.

Kubo lifetime and rolling-minute budgets still apply, including failed attempts. Configure adequate explicitly approved budgets for the transfer. If a recording exceeds the remaining rate allowance, it fails without a hidden queue or automatic retry, potentially after partial upload. Account-wide/cross-tab scheduling and persistent restart recovery remain open work. This API does not label data replicated merely because CIDs exist.

Twenty-four focused unit cases use real encryption and cover multi-block round trip, partial provider failure, revocation, tampering/key/binding rejection, malformed grants, cancellation, snapshots and overlapping whole-file operations. PR CI extends the real Chromium distinct-origin Kubo fixture with a two-block composed encrypted upload and authenticated download. The provider remains a protocol substitute; this is not live Kubo/provider qualification, native UI integration or scheduled multi-client acceptance.


## Explicit prepared upload recovery

`prepareUpload(plaintext, binding)` encrypts once without provider traffic and returns an in-memory handle with `status()`, `resume()` and `dispose()`. Only one prepared recording may occupy a composition at a time; ordinary uploads/downloads are refused until it completes or is disposed. `resume()` sends sequentially from the last acknowledged block. Provider/rate failure retains the same ciphertext and key for an explicit later call; it never schedules a retry or replenishes the Kubo client's lifetime/rate budgets. An acknowledgement lost after provider storage may cause that block to be resent with the same CID. Acknowledged blocks are not resent or assumed durable.

Statuses are `local-only`, `uploading`, `unavailable`, `acknowledged`, `disposed` and `expired`, with acknowledged/total block counts. Status contains no key or manifest. Only complete `resume()` returns grant material. Success transfers a key copy to the caller and overwrites retained source bytes/key. Dispose, abort, observed revocation and a fixed 15-minute deadline terminate the handle and overwrite retained bytes/key. Suspended execution can delay timer cleanup; each subsequent access checks monotonic elapsed time and clock rollback too. This is best-effort local memory cleanup, not physical erasure of browser/crypto/provider copies. Dispose does not cancel an already dispatched provider request; the shared signal and Kubo request deadline still govern it, and late acknowledgements cannot return a grant.

Retention is memory-only and bounded by the existing media size limit, one prepared upload per composition, and the fixed deadline. Browser closure loses the handle; no key/ciphertext is persisted for restart recovery. Calling many factories does not create an account-wide quota. Large recordings must fit the caller-approved budgets and retention window; expiry or exhausted lifetime quota may still require a new upload. The one-shot `upload()` behavior is unchanged.

PR unit tests cover byte-identical retry of the failed block, one retained reservation, overlapping resume refusal, disposal while awaiting acknowledgement, key/material cleanup, abort/revocation and expiry/clock rollback. Real Chromium CI forces the second block to fail, explicitly resumes it with the identical CID, proves the first is not resent and decrypts the completed two-block recording. Its provider remains a Kubo protocol substitute.


## Explicit prepared download recovery

`prepareDownload(manifest, key, binding)` accepts current authenticated private grant material, snapshots the key/binding, and reserves the composition without provider traffic. `resume()` retrieves sequential blocks, checking their exact lengths and CIDs before retaining them. If a provider request fails, only previously verified ciphertext blocks remain. An explicit later resume requests the failed block again without refetching verified blocks. There is no automatic retry, provider fallback or rate/lifetime-budget reset.

No partial plaintext is exposed. Once all blocks are verified, the complete digest, envelope and AES-GCM binding must pass before plaintext is returned. Failure during final integrity/decryption terminates the handle rather than retaining an unusable grant. Status returns only `ready`, `downloading`, `unavailable`, `verified`, `disposed` or `expired` and block counts. Successful plaintext belongs to the caller; retained ciphertext/key copies are overwritten. The ordinary one-shot download is unchanged.

Prepared upload and download share one reservation per composition. Download retention uses the same fixed15-minute timer/monotonic-access deadline and dispose, abort and observed-consent checks. Suspended browser execution may delay physical cleanup; this is not a disk cache, cross-tab quota, streaming decoder or provider erasure guarantee. Browser closure loses progress. A pending request remains governed by the shared signal and Kubo deadline; a late response after disposal cannot release plaintext. Whole-file memory/copy and64MiB stored-media limits remain as documented above.

Unit coverage includes failed-block recovery, tamper rejection before retention, wrong-key terminal disposal, grant snapshots, overlap refusal, pending-request disposal and abort/revocation/expiry. PR Chromium coverage fails the second download block, explicitly resumes its CID without fetching the first again, and verifies the decrypted recording. It still uses an explicit Kubo protocol substitute, not live-provider qualification or native UI integration.

## Early integrity refusal for ordinary downloads

Ordinary `download()` verifies each owned block snapshot against its expected CID and rechecks current authority before requesting the next block. A bad first or middle block therefore stops later reads immediately, rather than consuming the remainder of a recording's transfer allowance. Failed unretained copies are overwritten, previously retained ciphertext and the working key are cleaned by the existing finalizer, and the operation slot is released for an explicit later attempt. No automatic retry or refund is added.

Complete manifest digest, envelope and AES-GCM/binding checks still run before any plaintext is returned. This makes the composition independently enforce per-block integrity even with an alternate block adapter; the ordinary Kubo client already verifies its own responses. Unit regression covers first/middle corruption in three-block media, explicit recovery after repair, current-authority loss during hashing, and refusal of a bad whole-recording digest despite valid block CIDs. Existing Chromium composed-transfer contracts continue in PR CI.

## Binding admission before downloads

Ordinary and prepared downloads now capture and validate tenant/object binding fields before copying the key, reserving prepared state or fetching blocks. Missing, malformed, zero-tenant or non-string values fail without provider traffic. A failed preparation releases the composition so a valid operation can follow. The same shared snapshot validator is used by media encryption/decryption to ensure field validation and authenticated additional data use identical strings, including when a caller supplies accessors.

This validates shape, not permission or a key's authenticity. Current authenticated grants remain the caller's responsibility; a well-formed but wrong binding still fails AES-GCM authentication before plaintext is returned. Existing formats and valid encrypted recordings remain compatible. No reader registration or native activation is added.

## Pending work after disposal

Disposing or expiring a prepared transfer immediately clears its retained key and ciphertext, but its active `resume()` continues to occupy the composition until the pending provider and crypto work settles. Ordinary transfers and new preparations are refused during that interval. This preserves the one-operation bound even when a block adapter ignores cancellation or Web Crypto is still running. Late completion returns neither a grant nor plaintext; successful and failed settlement both free admission for a new explicit operation if authority remains current. A prepared handle that is idle still releases admission immediately on disposal.

Unit regressions cover upload/download disposal and expiry during both successful and failed deferred provider requests, plus disposal during decryption and subsequent reuse of the composition. No reader registration, automatic retry, provider cancellation guarantee or native activation is added.
